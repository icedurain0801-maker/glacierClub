# 采集源实时同步进度设计

日期：2026-08-13

## 1. 目标

用户在“采集源与授权”页面点击“开始同步”后，不离开当前列表，即可实时看到本次任务的排队、执行和完成状态，以及本次抓取到的帖子详情。

本期展示：

- 本次已抓取帖子数；
- 新增、更新、未变化数量；
- 帖子标题、正文、发帖人平台 ID、昵称、发布时间；
- 每个帖子携带的评论数量及本次评论总数；
- 同步失败原因和最近更新时间。

当前 Q1 站点没有经过验证的权威评论正文接口。本期不展示或伪造评论正文；帖子详情内明确标注“评论内容接口暂不支持”。后续获得可靠接口后，再把评论正文接入相同的任务明细模型。

## 2. 已确认的交互方案

采用方案 B：在采集源列表当前行下方展开实时同步区域。

### 2.1 启动同步

用户点击“开始同步”后：

1. 按钮立即显示“提交中…”并禁止重复点击；
2. 服务端同步完成授权、能力和游戏状态校验；
3. 服务端立即创建状态为 `queued` 的同步运行记录并返回 `runId`；
4. 当前采集源行下方展开实时同步区域；
5. 页面开始每 1–2 秒轮询该运行记录。

页面不再因为提交成功而关闭管理区域或失去本次任务上下文。

### 2.2 行内实时区域

区域分为两部分。

#### 进度摘要

展示：

- 状态：排队中、同步中、已完成、部分完成、失败；
- 已抓取帖子数；
- 新增数；
- 更新数；
- 未变化数；
- 评论总数（帖子接口返回的评论计数之和）；
- 最近更新时间；
- 当前错误信息（存在时）。

状态映射：

| 后端状态 | 页面文案 |
|---|---|
| `queued` | 排队中 |
| `running` | 同步中 |
| `completed_full` | 完整完成 |
| `completed_authorized_scope` | 授权范围完成 |
| `partial` | 部分完成 |
| `failed` | 同步失败 |

#### 帖子结果表

字段：

| 字段 | 说明 |
|---|---|
| 标题 | 无标题时显示“无标题” |
| 发帖人昵称 | Q1 `user.personality.nickName` |
| 发帖人 ID | Q1 `user.account.id` |
| 发布时间 | 按管理端统一时间格式显示 |
| 评论数 | Q1 帖子接口返回的 `commentCount` |
| 入库结果 | 新增、更新、未变化 |

点击帖子行展开详情：

- 展示帖子正文；
- 正文过长时默认折叠，提供展开/收起；
- 展示评论数量；
- 展示“评论内容接口暂不支持”，不将评论数冒充评论正文。

新提交的批次追加到当前结果列表。为控制页面体积，前端首屏最多保留 100 条，更多内容通过“加载更多”读取；这不影响数据库中的完整任务明细。

### 2.3 任务恢复

- 页面刷新后，按采集源查找正在执行或最近一次运行并恢复展示；
- 列表同时只展开一个采集源的实时区域；
- 用户可手动收起，收起不终止后台任务；
- `queued` 或 `running` 时持续轮询；
- 进入终态后再刷新一次明细并停止轮询；
- 网络短暂失败采用递增间隔重试，页面显示“连接中断，正在重试”，不把任务误判为失败。

## 3. 后端数据模型

### 3.1 提交时创建运行记录

现状是 Worker 开始执行后才创建 `po_sync_runs`，无法让提交接口返回稳定任务 ID。调整为：

- `POST /sources/:id/sync` 在事务内创建 `po_sync_runs`；
- 初始状态为 `queued`；
- 同一事务完成同步模式保存、采集源启用和手动任务标记；
- 接口返回 `runId`、`status`、`mode` 和 `enabled`；
- Worker 领取该 queued run 并切换为 `running`，不再为同一请求创建第二条运行记录。

周期调度触发时，Worker 仍可自行创建运行记录，但必须沿用同一生命周期。

### 3.2 任务与内容的多对多关系

新增运行内容明细表，用于准确回答“本次同步抓到了哪些帖子”。建议表名：`po_sync_run_contents`。

核心字段：

| 字段 | 说明 |
|---|---|
| `run_id` | 同步运行 ID |
| `content_id` | 幂等内容表 ID |
| `change_type` | `inserted` / `changed` / `unchanged` |
| `sync_scope` | 本期主要为 `posts`，为未来评论保留 |
| `fetched_at` | 本次抓取时间 |
| `sequence_no` | 本次运行内的稳定展示顺序 |

唯一约束为 `(run_id, content_id, sync_scope)`。同一内容可关联多次运行，但 `po_contents` 仍保持 `(account_id, external_id)` 幂等，不重复创建。

不直接在 `po_contents` 增加单一 `sync_run_id`，因为同一帖子会被多次增量同步抓取。

### 3.3 实时计数

扩展 `po_sync_runs`：

- `fetched_count`：本次抓取条数，包含未变化内容；
- `inserted_count`；
- `changed_count`；
- `unchanged_count`；
- `comment_count`：帖子接口评论计数之和；
- `updated_at`：最近进度更新时间。

保留原有 `discovered_count`、`stored_count` 兼容现有逻辑；新页面使用语义更明确的新字段。

Worker 每完成一页数据库事务时，同时：

1. 幂等写入或更新 `po_contents`；
2. 写入本次运行与内容的关联及变化类型；
3. 累加本次运行计数；
4. 更新同步断点；
5. 提交事务。

因此页面不会看到计数已增加但帖子明细尚未入库的中间状态。

## 4. API 设计

### 4.1 开始同步

`POST /sources/:sourceId/sync`

请求：

```json
{ "mode": "incremental" }
```

响应：

```json
{
  "data": {
    "queued": true,
    "enabled": true,
    "runId": "...",
    "accountId": "...",
    "mode": "incremental",
    "status": "queued"
  }
}
```

### 4.2 获取运行进度

`GET /sync-runs/:runId`

返回运行状态、各类计数、时间、错误以及帖子/评论阶段摘要。响应不包含凭据、原始 Token 或连接器请求头。

### 4.3 获取本次帖子明细

`GET /sync-runs/:runId/contents?scope=posts&after=<sequence>&limit=50`

返回：

- 本次运行序号；
- 变化类型；
- 内容 ID 和外部 ID；
- 标题、正文；
- 发帖人 ID、昵称；
- 发布时间；
- 评论数；
- 下一页游标。

只允许读取属于该运行账号、采集源和游戏范围的内容。

### 4.4 按采集源恢复最近任务

`GET /sources/:sourceId/sync-runs/latest`

优先返回 `queued/running` 任务，否则返回最近一次终态任务。用于页面刷新后的恢复。

## 5. 实时传输方案

本期采用短轮询，不使用 WebSocket。

理由：

- 当前管理端是原生 JavaScript；
- API 与 Worker 是独立进程，没有消息代理；
- 每页数据已通过数据库事务提交，数据库是可靠状态源；
- 1–2 秒刷新满足管理后台可见性要求；
- 比 SSE/WebSocket 更容易处理页面刷新、重连和多实例。

轮询策略：

- `queued/running`：每 1.5 秒请求运行进度；
- 只有 `fetched_count` 或 `updated_at` 变化时才请求新增明细；
- 使用 `after=sequence_no` 增量获取，避免反复下载历史正文；
- 连续失败后退避到 3 秒、5 秒、10 秒；
- 恢复成功后回到 1.5 秒；
- 终态停止定时器。

## 6. 评论边界

本期 Q1 评论能力状态维持 `unsupported`。

页面可以展示：

- 帖子自带评论数；
- 本次抓取帖子的评论数合计。

页面不得展示：

- 未经权威接口获取的评论正文；
- 从页面 HTML、私有未验证端点或推断数据伪造的评论；
- 将评论数量误标为“已抓取评论数”。

文案固定为：“该站点当前仅提供评论数量，评论内容接口暂不支持。”

未来接入评论接口时，评论内容作为 `sync_scope=comments` 写入相同运行明细体系，并在帖子详情中按父子关系展开，无需推翻本期结构。

## 7. 异常与边界

- 授权失败、账号不可用、游戏停用：不创建可执行运行，接口返回明确错误；页面不展开伪进度。
- Worker 尚未领取：保持 `queued`，展示排队时长。
- 单页抓取失败：运行记录写入错误码和错误信息，已提交的页面结果仍可查看。
- 重复点击：按钮提交态锁定；后端对同一 source 的 queued/running 运行进行幂等复用或返回冲突，避免并行重复任务。
- 帖子无标题、无昵称或无发布时间：显示统一缺省值，不影响同步。
- 正文包含特殊字符：前端继续通过转义函数渲染，禁止直接拼接不可信 HTML。
- 大数据量：明细游标分页，前端虚拟化不是本期必要范围。
- 页面切换或关闭：清理轮询计时器；后台任务继续执行。
- 凭据安全：实时接口只读取运行和内容数据，绝不返回、记录或重新解密 Token。

## 8. 测试与验收

### 后端

- 开始同步原子创建 queued run、启用源并入队；
- 授权失败不创建运行、不启用、不入队；
- Worker 领取 queued run，不重复创建；
- 每页事务同时更新内容、运行关联、计数和断点；
- `inserted/changed/unchanged` 统计正确；
- 第二次同步内容幂等，但运行明细仍记录 fetched/unchanged；
- 运行详情和游标明细接口分页正确；
- 不同 source/account 的任务明细不可串读；
- 评论正文不支持时能力和页面契约明确。

### 前端

- 点击“开始同步”后当前行展开且显示排队中；
- 状态与计数按轮询更新；
- 新帖子只追加一次；
- 帖子字段完整，正文可展开/收起；
- 评论数与“不支持评论正文”文案正确；
- 完成/失败后停止轮询；
- 刷新页面能恢复运行中的任务；
- 网络失败后重试且不误报任务失败；
- 切换页面后无残留轮询。

### 真实验收

使用现有 Q1 正式采集源：

1. 点击开始同步；
2. 验证先显示排队中，再显示同步中；
3. 验证每批抓取后数量和帖子行追加；
4. 抽查标题、正文、发帖人 ID、昵称、发布时间和评论数与数据库一致；
5. 验证同步完成后终态和最终计数一致；
6. 再执行一次，验证内容不重复且本次运行显示未变化条数；
7. 全程确认凭据不出现在响应、日志、页面或文档中。

## 9. 非本期范围

- 逆向或猜测 Q1 评论正文接口；
- WebSocket、Redis 或消息队列；
- 评论正文、评论作者和评论回复展示；
- 大规模虚拟滚动、导出和跨任务比较；
- 修改现有内容管理页的信息架构。
