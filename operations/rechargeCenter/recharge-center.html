需求说明
角色验证登录 — 需求说明
所属模块：账号 / 登录中心 优先级：高 应用场景：红钻充值页 + 企微活动页 仅角色维度 验证码有效期 24 小时
1需求概述

背景：当前网页活动在引导玩家参与时，缺少一套轻量、无需账号密码、可独立验证玩家身份的登录方式。玩家在网页侧往往只知道自己的游戏角色，并不记得平台账号密码，传统账密登录在活动场景下转化率低、流失严重。

定位：新增「角色验证登录」能力——以游戏角色为身份锚点的轻量登录，登录态只到角色维度（角色 ID + 角色名 + 区服），不涉及账号体系。验证码不发短信/邮箱，而是发到游戏内角色的邮件，玩家凭角色邮件里的验证码完成身份核验。

核心逻辑（两个活动页完全一致）：校验角色 ID 有效性 → 向该游戏角色发送一封含验证码的游戏内邮件 → 玩家在游戏里拿到验证码后回网页端填写 → 验证成功即以该角色身份登录本次网页活动。

应用场景：本次落地红钻充值页与企微活动页两个活动；二者的角色验证登录操作逻辑完全相同，差异仅在入口形态（见第 3 节）。

2角色验证登录通用流程

两个活动页共用同一套操作逻辑：

  1. 玩家输入角色 ID，失焦即校验该角色是否真实存在；校验通过后回显「角色ID - 角色名 - 区服」供玩家确认。
  2. 角色校验成功后，「获取验证码」按钮才高亮可点击；校验失败按钮保持置灰不可点。
  3. 点击获取验证码 → 调用游戏侧发件接口，向该角色游戏内邮箱发送含验证码的邮件（6 位数字，有效期 24 小时）；按钮进入 60s 倒计时防刷。
  4. 玩家在游戏内读取验证码，回填登录页。
  5. 系统校验「角色 ID + 验证码」匹配且未过期 → 以角色身份登录该网页活动，登录态 = 角色 ID + 角色名 + 区服。
为什么用游戏内邮件：能在游戏里收到并读取该角色的邮件，即证明操作人拥有此角色，无需再依赖手机号/邮箱等账号资产，验证与角色身份天然绑定。
3两个活动页的入口形态
A红钻充值页（定制登录页）入口内嵌

红钻充值页的登录页面为定制化页面，不复用通用页。直接在原「账号登录」页顶部增加一个「角色验证登录」Tab，与「账号登录」并列切换：

  • 角色验证登录 Tab：输入框为角色 ID + 验证码，操作逻辑同第 2 节。
  • 账号登录 Tab：保持原有账密登录逻辑不变。
  • 两个 Tab 共用底部「登录」按钮与协议勾选。
B企微活动页（复用通用页）独立页面

企微活动页点击「登录」后弹出登录方式选择弹窗，除「账号登录」外新增「角色验证登录」。其中：

  • 「角色验证登录」为本次新增的通用独立页面，从弹窗点击后跳转至该独立页，输入角色 ID + 验证码完成登录。
  • 该通用页与具体游戏 / 活动解耦，后续其他游戏、其他活动可直接复用，无需重复开发。
  • 登录成功后以角色身份回带登录态至当前活动页。
A 为充值页专属的定制内嵌 Tab，B 为可被多个活动/游戏复用的独立页面；二者界面承载不同，但角色验证登录的字段、校验、发码、时效逻辑完全一致。
4角色验证登录字段定义

下列字段在「红钻充值页定制 Tab」与「企微通用独立页」中保持一致：

字段控件必填校验 / 说明
角色 ID文本输入是失焦即校验角色是否存在；不存在时下方红字提示「未找到该角色ID，请检查后重试」，并禁用「获取验证码」
角色信息回显文本（只读）—角色校验通过后展示「角色ID - 角色名 - 区服」，供玩家确认身份

验证并登录按钮—角色 + 验证码均填写后可提交；成功后产出角色维度登录态
5后端安全性校验

本登录无账密、纯靠角色 + 验证码，安全性全部由后端兜底，前端只做基础体验校验，所有关键判定以后端为准。两个活动页接入同一套后端能力。

验证码安全
  • 服务端生成与比对：验证码由后端生成并与角色 ID 强绑定存储（建议加盐哈希），前端不持有明文、不参与比对。
  • 时效与一次性：有效期 24 小时；一经验证成功立即作废，禁止重复使用；重新获取后旧码失效。
  • 错误次数限制：同一角色/同一码连续错误达上限（建议 5 次）即作废并锁定一段时间，防暴力枚举。
发码与请求防刷
  • 发码频控：同一角色 60s 内仅可发一次；同一 IP / 同一活动来源设日发码上限，防轰炸式刷邮件。
  • 角色存在性后端校验：角色 ID 是否存在由后端裁定，不存在直接拦截、不发码，避免向不存在角色发件及探测。
  • 接口限流与风控：发码、校验接口均接入限流与风控，识别批量/异常来源请求并拦截。
登录态与回跳安全
  • 登录凭证：登录成功下发短时效、一次性票据（ticket），活动侧凭票据换取正式登录态，票据用后即焚、不可重放。
  • 回跳地址白名单：redirect 必须命中后端域名白名单，否则拒绝跳转，防开放重定向。
  • 凭证不可伪造：回带凭证由后端签名，活动侧校验签名，防止前端伪造角色身份。
原则：前端的角色校验、倒计时、按钮置灰等仅为体验优化，不可信；是否发码、验证码是否正确、角色是否存在、能否登录、回跳是否合法，全部以后端校验结果为准。
