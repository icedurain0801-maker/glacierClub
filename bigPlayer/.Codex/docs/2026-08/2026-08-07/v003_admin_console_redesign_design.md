## 1. 背景与问题诊断

### 1.1 触发点
P0 后端 pipeline（采集→去重→规则粗筛→AI 精析→双口径告警→钉钉推送）已实现并通过 44 项单测，真实 MariaDB E2E 跑通。但后台前端「太潦草」，无法交付使用。

### 1.2 根因：需求阶段未设计过「后台交互」
v001 设计文档约 95% 篇幅在规划后端 pipeline。关于前端仅有第 9 节，且只做了一件事——**把 6 个只读接口的数据摆到页面上**。后台「潦草」不是实现偷懒，而是**从设计阶段就缺少「运营在后台要完成哪些任务、如何操作」这一层**。

### 1.3 当前后台三个硬伤

| # | 问题 | 表现 |
|---|------|------|
| 1 | 纯只读，运营干不了活 | 需求要求运营「自选平台」「在线编辑关键词规则(Q6)」「配置采集频率/生效时段(Q5)」「管理凭据授权(Q3)」，当前后台**这些编辑入口全部缺失**。采集配置 tab 状态列写死「启用需走配置接口」。 |
| 2 | 两个按钮是坏的 | 「立即采集」仅弹 toast 占位；「停用/启用」调 `PATCH /sources/:id`，**后端无此路由**，点击直接报错。 |
| 3 | 信息架构混乱 | 单页塞 5 概览卡 + 3 tab，把「日常监控看板」与「系统配置管理」两种不同心智、不同使用频率的场景硬揉在一起。 |

### 1.4 需求 ↔ 现状差距全景

| 需求文档要求 | 后端 | 后台前端 |
|---|---|---|
| 概览看板（趋势/告警/来源/热帖）| ✅ | ✅ 已有 |
| 内容列表 + 情感过滤 | ✅ | ✅ 已有 |
| 告警处置闭环（改状态/备注）| ✅ | ✅ 已有 |
| 自选平台 / 数据源开关（Q1、Q5）| ⚠️ 无写接口 | ❌ 假按钮 |
| 关键词规则在线编辑（Q6 两级 + Q7 双口径）| ⚠️ 无写接口 | ❌ 完全没有 |
| 采集频率 / 生效时段配置（Q5）| ⚠️ 无写接口 | ❌ 完全没有 |
| 凭据授权管理（Q3 secret_ref）| ⚠️ 无写接口 | ❌ 完全没有 |
| 手动触发采集（验收①要能跑通）| ⚠️ 无写接口 | ❌ 假按钮 |

**结论**：后台从「只读 dashboard」升级为「运营可真正配置和操作的控制台」，需要**补后端写接口 + 重构前端信息架构**。

## 3. 架构总览

侧边栏 5 个独立页面，**监控（天天看）与配置（偶尔改）彻底分开**：

```
舆情分析
├─ 监控看板      日常盯盘：5 指标卡 + 7 日趋势 + 当前告警 + 来源分布 + 负面热帖
├─ 内容活流      帖子/评论列表 + 情感/平台/关键词过滤 + 详情抽屉（AI 分析）
├─ 告警处置      双口径告警闭环：列表 + 状态机(待处理→处理中→已处理/误报) + 备注
├─ 采集源与授权  平台开关 + 频率/生效时段 + 凭据授权(加密) + 手动触发采集
└─ 关键词规则    游戏×平台两级词表 + 分组 + 双口径(即时/聚合) + 阈值/时间窗
```

现有「单页 5 卡 + 3 tab」→ 拆成前 5 页。监控看板保留现有可视化，真正新建的是后两页的配置能力。侧边栏复用 `admin/shared/sidebar`，5 页各自独立 HTML 入口或单壳内路由（实施阶段定，倾向各自独立 HTML 以匹配现有 admin 多页习惯）。

## 4. 页面设计

### 4.1 页① 监控看板（现有能力打磨，非重建）
保留：5 指标卡、近 7 日情感趋势柱状、当前告警、来源分布、负面热帖 Top10。
打磨：
- **空状态**：干瘪一行字 → 带图标 + 引导语（「暂无告警，系统运行正常」/「还没有采集源，去『采集源与授权』添加」）。
- **加载态**：白屏 → 骨架屏/loading。
- **错误态**：仅 toast → 页面级错误提示 + 重试按钮，区分「服务未启动」vs「无数据」。
- 顶部游戏选择器、刷新按钮保留；「立即采集」按钮移出概览页（归入页④，避免误导）。

### 4.2 页② 内容活流（现有能力打磨）
保留：内容表格（内容/来源/情感/风险等级/发布时间/操作）、平台过滤、情感过滤、关键词搜索、详情抽屉。
补齐：
- 情感过滤增加 `unclassified`（未析内容，对应 Q-未命中「只存档不析」）。
- 详情抽屉展示 AI 分析（情感/负面强度/话题/命中关键词/摘要）、来源信息。
- 空/加载/错误态同页①。

### 4.3 页③ 告警处置（现有能力打磨 + 补字段）
保留：告警表格（等级/事项/游戏/状态/时间/负责人）、处置抽屉（状态机 + 备注）。
补齐：
- 抽屉展示**关联内容列表**（po_alert_contents）、**钉钉推送状态**（not_sent/sent/failed）。
- 列表增加 `alert_type` 展示（区分 immediate/aggregate 双口径）。
- 状态机流转沿用现有 PATCH /alerts/:id。

### 4.4 页④ 采集源与授权（**新建配置能力，当前最大缺口**）
每个采集源一行，可展开配置：

| 区块 | 交互 | 对应需求 |
|------|------|---------|
| 平台开关 | 启用/停用 toggle，实时生效 | Q1 自选平台 |
| 采集频率 | 下拉/输入：15 分/30 分/1 小时/自定义 | Q5 频率可配 |
| 生效时段 | 星期多选 + 时间段（支持跨天，对应 active_window JSON）| Q5 |
| 凭据授权 | 输入框填 Cookie/token → 后端加密存；页面只显示「已配置✓/有效期/最近校验」，**永不回显明文**；「检测授权」触发 healthCheck | Q3（加密折中，见 §6.4）|
| 手动触发 | 「立即采集」→ 真正调后端入队，带结果反馈 | 验收① |
| 状态列 | 未配置/已授权/已过期/失败(附原因) | Q3 fail-closed |

### 4.5 页⑤ 关键词规则（**新建，省 token 与告警准确度的命门**）
游戏选择器 → 该游戏下按**分组**管理，每组一张卡片：

```
┌─ 分组：炸服类  [即时告警 immediate ▾] [紧急 ▾]              [删除组]
│  关键词：炸服 ✕  登不上 ✕  连不上 ✕  [+ 添加词]
│  生效平台：○游戏级默认  ●仅 TapTap  ○仅 B站   (平台级覆盖 Q6)
│  ─ 即时口径无需阈值，命中单条即报 ─
├─ 分组：差评轰炸  [聚合告警 aggregate ▾] [关注 ▾]           [删除组]
│  关键词：垃圾游戏 ✕  退钱 ✕  骗氪 ✕  [+ 添加词]
│  聚合阈值：[30] 分钟内命中 [5] 条触发         (Q7 window/threshold)
└─ [+ 新建分组]                                    [保存全部规则]
```

- **两级(Q6)**：每组选「游戏级默认(全平台，platform=NULL)」或「平台级覆盖(仅某平台)」；平台级空时回退游戏级。
- **双口径(Q7)**：immediate 组隐藏阈值/时间窗；aggregate 组显示 window_seconds + threshold_count。
- **保存前校验**：空组、重复词、阈值合法性（正整数、时间窗 > 0）。
- 严重等级：urgent/attention/normal（对应现有 severity 枚举）。

## 5. 后端写接口（新建，配合前端）

当前后端仅只读接口。新增：

```
PATCH  /sources/:id              数据源开关 / 频率 / 生效时段
PUT    /sources/:id/credential   凭据（加密存，不回显）
POST   /sources/:id/check-auth   检测授权（触发 connector.healthCheck 回写状态）
POST   /sources/:id/collect      手动触发采集入队
GET    /keyword-rules?gameId=    读词表（两级：平台级 + 游戏级默认）
PUT    /keyword-rules            批量保存词表（分组/双口径全量提交）
```

- 全部沿用现有契约：成功 `{data, meta}`，失败 `{error:{code,message,details}}`，HTTP 200/400/404/500。
- fail-closed 语义不变：未授权源手动采集返回 UNAUTHORIZED，不伪造数据。
- `PUT /keyword-rules` 采用全量提交 + 事务替换该 game 的规则集（先删后插或差量 upsert，实施阶段定；MySQL 无 DDL 事务但 DML 有事务，走 DML 事务保证原子）。

## 6. 关键设计取舍

### 6.1 为什么多页面而非单页多 tab
监控（高频只读）与配置（低频写操作）是两种心智。配置表单（生效时段、关键词分组卡片）塞进 tab 会严重拥挤。多页面职责单一，也更贴合现有 admin 多页习惯，便于交接。

### 6.2 关键词全量保存而非逐条 CRUD
运营编辑词表是「一批一起改」的心智；逐条 PATCH 会产生中间不一致状态（如删了组但词还在）。全量提交 + 后端事务替换，前端交互也更简单（一个「保存全部」）。

### 6.3 手动触发采集走「入队」而非「同步跑」
采集可能耗时，同步会阻塞 API 请求。POST /collect 只入队并立即返回「已提交」，Worker 到期或被唤醒后执行，前端轮询/刷新看结果。契合方案乙 Server/Worker 解耦。

### 6.4 凭据授权：UI 可填但加密存、不回显（对 Q3 的折中）
- **背景**：v001 Q3 硬约束是凭据只存 secret_ref 引用、绝不落明文。运营诉求是「在 UI 里完成授权，不想上服务器改环境变量」。
- **红线**：明文凭据流经浏览器（内存/XSS/HAR 抓包风险）+ 明文入库（拖库即账号接管）+ 交接合规问题。这些是公司官方账号登录态，泄露等于账号被接管。
- **折中方案**：前端可填/更新凭据 → HTTPS 提交 → 后端用 `CREDENTIAL_ENC_KEY`（环境变量）**AES 加密后存 po_credentials**（或写密钥库只留引用）；页面**永不回显**明文，只显示「已配置✓/有效期/最近校验状态」，可「重新填写」覆盖但看不到旧值；保留「检测授权」验活。
- **状态**：用户未在明文/加密间明确作答，采用此最稳妥判断，用户可随时推翻。若用户坚持明文存储，需在文档显式标注为知情同意的例外。

## 7. 分阶段实施

「全都要」，但按依赖顺序落地，每阶段可独立验证：

- **阶段 A（地基）**：后端 6 个写接口 + 凭据 AES 加密 + Repository 写方法 + 单测。前端依赖它，先行。
- **阶段 B（新建两页）**：页④采集源与授权、页⑤关键词规则。接通阶段 A 接口。
- **阶段 C（架构 + 打磨）**：信息架构拆分（单页 → 5 页侧边栏）+ 三个监控页视觉打磨（空/加载/错误态）。

## 9. 验收标准

1. 侧边栏 5 页可正常切换，监控与配置分离；
2. 页④：平台开关实时生效、频率/生效时段可配可存、凭据可填且加密存不回显、检测授权可触发、手动采集可入队并反馈；
3. 页⑤：游戏×平台两级词表可编辑、分组增删、双口径(即时/聚合)阈值可配、保存前校验、保存后 pipeline 生效；
4. 6 个新写接口全通，契约一致，fail-closed 不伪造数据，凭据不明文落库、不回显；
5. 三个监控页空/加载/错误态完善，无假按钮、无「走配置接口」死链；
6. 全流程真实 MariaDB 验证，新增单测覆盖写接口。
