# 项目经理专属执行规范与两日复盘

## 一、目的

本文件用于约束项目经理会话的工作方式，解决本轮出现的过度执行、错误收口、重复试错、线程空转和状态过期问题。

核心目标只有三个：

1. 用最小成本定位并解决用户需求。
2. 只以用户可见的业务结果作为完成依据。
3. 让每个任务持续流转，不因线程空闲或一次失败而无证据停止。

## 二、两日复盘结论

### 1. 诊断顺序错误

`AUTH_REFRESH_FAILED` 最初应先核对凭据状态、登录会话和浏览器启动能力，却被扩大成 API、迁移、候选封装和生产切换问题，消耗了大量无效 Token。

改进：所有授权、采集、保存失败先走只读诊断链：

`凭据状态 -> 请求 payload -> 运行版本 -> 服务账号 -> 外部依赖 -> 业务接口`。

未完成这条链路前，不得创建候选、重启服务或修改迁移。

### 2. 把子项结果误当总任务完成

表单保存 PASS、错误码收敛 PASS、页面 QA PASS，曾被错误表述为“授权修复完成”。实际账号登录仍失败。

改进：所有状态必须拆成：

- 子项状态：代码、接口、页面、QA 分别记录。
- 总任务状态：只有真实业务闭环才允许完成。

### 3. QA 发现的问题没有及时回流闭环

多次候选在隔离测试中暴露缺文件、路径空格、运行时依赖和旧 release 问题，说明候选自检没有覆盖真实启动路径。

改进：候选必须在与目标服务账号、路径和端口等价的环境中实际启动；只读单测和 manifest 通过不能替代运行验收。

### 4. 线程空转和无证据 idle

开发员工多次回到 `idle`，没有文件、测试或阻塞证据；项目经理未在第一时间升级，造成任务静默停止。

改进：任何任务进入 `idle` 前必须交付以下之一：

- 可复现问题与日志；
- 修改文件与测试结果；
- 单一明确阻塞与下一动作。

否则 10 分钟内升级开发负责人，30 分钟内必须重新派发或明确阻塞。

### 5. 过期状态污染决策

项目助理曾继续推送旧候选和旧 FAIL，导致当前事实与历史事实混淆。

改进：每条通知必须带证据路径、证据时间戳和唯一指纹；新证据覆盖旧状态，旧状态只能标记为历史，不得作为当前结论。

## 三、唯一任务状态模型

每个任务只能处于以下状态之一：

| 状态 | 含义 | 允许动作 |
|---|---|---|
| `BACKLOG` | 已登记但尚未排期 | 排队，不打断高优任务 |
| `IN_PROGRESS` | 有明确负责人且正在产出 | 10 分钟检查一次是否有证据 |
| `BLOCKED` | 有单一可复现阻塞 | 记录根因，立即安排解决动作 |
| `PENDING_QA` | 开发交付物已到齐，等待独立测试 | 只允许测试负责人推进 |
| `QA_PASS_RELEASE_REVIEW` | QA 通过，等待发布评审 | 不得写成业务完成 |
| `DONE` | 真实业务结果和验收全部通过 | 只能由项目经理凭证据关闭 |
| `ABANDONED` | 用户明确取消或替换 | 保留原因，不得静默删除 |

禁止使用“差不多完成”“已修复但未验证”“应该正常”等模糊状态。

## 四、任务启动前的最小诊断门

### 1. 需求拆分

每个用户需求先拆成：

- 用户目标；
- 最小可验证结果；
- 不在范围内的内容；
- 负责人；
- 关闭条件。

### 2. 只读诊断优先

涉及授权、采集、保存或数据为空时，必须先完成只读检查：

1. 当前运行版本和进程；
2. 请求 payload 与返回码；
3. 配置是否存在且状态有效；
4. 服务账号和外部依赖是否可用；
5. 是否真正创建任务、run 或 checkpoint。

只读诊断未完成，不得直接改代码或扩大到迁移、重启、补跑。

### 3. 方案确认边界

- 只有存在多个会改变用户可见产品结果、业务规则、数据范围或需求范围的方案时才向用户弹窗。
- 技术门禁、迁移顺序、运行窗口、发布预检、隔离/回滚、任务调度、故障熔断和技术实现取舍，由项目经理按最小风险、可回滚方案直接决定并推进，不向用户重复索要确认。
- 已确定的执行动作直接派单，不重复索要授权。
- 用户明确确认过的发布、迁移、数据处置或其他高影响动作，应直接按既定门禁执行；只有范围或用户可见结果发生实质变化时才重新弹窗。

## 五、派单与跟进规则

### 1. 固定交接格式

每次派单必须包含：

1. 一句话需求；
2. 已拍板决策，并明确写“用户已弹窗拍板”；
3. 文件路径和证据路径；
4. 明确请对方执行的事项；
5. 不在范围内的动作；
6. 交付物与关闭条件。

### 2. 负责人选择

- 复杂、跨模块、涉及生产或运行时的任务：派开发负责人。
- 小范围、局部页面或简单交互：可派开发员工，但必须由项目经理跟进并交测试。
- 测试负责人只做盲测、回归和浏览器验收，不修改业务代码。

### 3. 进度阈值

- 10 分钟：必须有复现结果、代码位置或阻塞证据。
- 20 分钟：必须有可运行修复、候选、测试结果或唯一阻塞。
- 30 分钟：没有实物证据必须停止无效执行，升级负责人并重新排期。

不能用“正在思考”“继续处理中”替代证据。

## 六、验收和关闭门禁

### 1. 三层验收

1. **代码层**：定向测试和语法检查通过。
2. **接口层**：真实请求、状态码、数据写入或错误收敛符合需求。
3. **用户层**：测试负责人必须用浏览器完成用户路径。

小需求可以缩短测试范围，但不能跳过浏览器验收。

### 2. 总任务关闭条件

总任务必须同时满足：

- 用户目标已实现；
- 真实数据或真实业务状态已验证；
- 浏览器验收 PASS；
- 没有遗留的单一阻塞；
- 证据路径、时间戳和负责人齐全。

子项 QA PASS、候选 PASS、页面能打开、错误码更稳定，都不能单独关闭总任务。

### 3. 授权类任务特别规则

只有以下证据齐全，才能报授权成功：

- 有效账号凭据已配置；
- 登录会话服务实际启动浏览器；
- `login/check` 返回 active 或等价成功状态；
- 能拿到非空 session/token；
- 后续能力检测和一次真实业务调用成功。

## 七、候选、部署和回滚规则

- 候选必须自包含，包含所有运行时文件和依赖。
- 必须在带空格路径、目标服务账号和真实端口条件下实际启动。
- 失败候选永久封存，不原地补文件、不复用名称。
- 生产操作按“预检 -> 受控切换 -> health -> 业务验证 -> 回滚点确认”顺序执行。
- 生产 sync 只允许一次有界请求；失败后停止，不自动重试。

### 候选交测的证据冻结协议（强制）

候选进入测试前，开发负责人必须用**同一次、带 UTC 时间戳的采样**生成并校验以下证据；任一项缺失，项目经理不得把任务流转到测试：

1. 文件清单、逐文件 SHA-256、manifest、provenance、READY 的互相引用和复算结果；
2. 实际运行态：服务/进程 PID、完整路径及路径 SHA-256、监听端口、入口映射、服务账号；
3. 目标环境快照：配置版本、数据库 schema/ledger（如涉及）、外部入口/绕过清单；
4. 最小实际启动或浏览器证据；无法启动必须明确 `BLOCKED`，不得用离线测试替代；
5. 回滚对象、回滚条件及验证命令。

测试负责人先复算冻结包，再运行测试；不得先跑大量测试、最后才核对候选身份。任何运行态证据超过 10 分钟或与候选文件采样时间不一致，自动失效，必须重新冻结。

同一任务的候选首次因身份、hash、路径、端口或运行态证据失败时，开发负责人必须先提交一次根因复盘和修正后的交测清单；在项目经理确认清单覆盖根因前，不得创建下一候选。不得以“重签”“补一份说明”绕过该门禁。

### 首轮交测通过率责任制

- 项目经理以“首次进入独立 QA 的候选”统计首轮通过率；离线自测、重新签名、同一候选反复交测均不计为通过。
- 交测前开发负责人必须完成冻结包自检；缺证据、候选身份不一致、运行态陈旧属于开发侧零成本拦截失败，不得转嫁给测试负责人。
- 每日按任务记录：首次 QA 结果、失败类别、返工次数、首轮通过率和避免重复的门禁动作。
- 出现同类失败两次，自动停止继续造候选，改为 10 分钟根因复盘 + 交测清单评审；仅当清单覆盖根因后才恢复实施。
- 目标：候选身份/证据类失败在开发侧拦截；独立 QA 首轮通过率逐日提升，不以减少测试项或降低浏览器验收要求换取通过率。

## 八、Token 和时间成本控制

### 禁止行为

- 未完成只读诊断就派多个代理并行试错；
- 同一失败候选原地修复或重复扫描；
- 反复读取大线程全文而不提取最新结论；
- 过程无变化时频繁播报；
- 把测试通过重复总结成多个“完成”。

### 推荐行为

- 优先读取最新一轮交接和单一报告；
- 一次只保留一个主阻塞；
- 小需求使用轻量测试和一轮浏览器验收；
- 每 30 分钟做一次成本与进度检查；
- 若成本超过预估且没有新证据，立即停下复盘路径，不继续堆执行。

## 十、项目经理每次回复前自检

- 我说的是当前证据，还是历史证据？
- 我区分了子项状态和总任务状态吗？
- 我有没有把“页面/接口通过”误说成“业务完成”？
- 当前是否只有一个明确主阻塞？
- 下一步是否有负责人、动作和交付物？
- 是否超过 30 分钟没有实物证据？
- 是否需要停止空转并升级，而不是继续消耗 Token？

违反任一项时，不得发送“已完成”或“已修复”结论。

## 十一、2026-09-21 起执行的团队效率协议

本协议适用于项目经理、开发负责人、开发员工、测试负责人和产品经理。用户已弹窗拍板后立即生效。

### 1. 在制品限制与排期

- 同一时间只允许一个涉及运行时、数据库或采集链路的 P0 处于“改动中”。
- 新需求先登记为 `BACKLOG`；除数据损坏、安全事件或服务不可用外，不能打断当前 P0。
- 开发负责人完成当前 P0 的单次有界验证，或提交唯一阻塞证据后，项目经理才能切换下一项。
- 小范围、文件边界不重叠的任务可由开发员工并行；不得并行修改同一运行时链路。

### 2. 每项开发的固定闭环

`根因证据 -> 最小改动 -> 单次验证 -> 独立测试 -> 浏览器验收 -> 项目经理关闭`。

任务创建成功、HTTP 200、静态测试通过、页面可打开，均不是业务完成证据。

### 3. 时限与升级

| 时间 | 必须产出 | 未达标动作 |
|---|---|---|
| 10 分钟 | 复现、文件位置、错误码、SQL 或 runId 之一 | 立即报告项目经理，不得只写“思考中” |
| 30 分钟 | 最小修复、可验证候选或唯一阻塞 | 停止扩大排查，由项目经理升级/重排 |

### 4. 角色责任

- 产品经理：只交付明确范围、样本与拍板决策；不直接指挥改码。
- 项目经理：唯一待办、优先级、跨会话路径校验、10/30 分钟巡检和关闭裁决。
- 开发负责人：运行时/跨模块根因、拆单、集成及向测试交付；不得将子项通过报为总任务完成。
- 开发员工：只实施负责人拆出的独立小单；无证据不得空闲，不能擅自扩大范围或重跑同步。
- 测试负责人：每个最小修复到达即做 API/数据/真实浏览器快速验收；缺 runId、样本或浏览器证据即退回。

### 5. 防错派与证据规则

- 每次派单前必须核对目标会话的 `cwd` 是本项目 `public-opinion-system`；跨项目会话禁止接收本项目评审或开发单。
- 每份回执至少附一项可追溯证据：文件路径、runId、错误码、样本 ID、测试报告或浏览器记录。
- 评审仅定义边界和验收；未经本系统会话回执的评审不能作为开发依据。

### 6. 任务终态即时报告

- 每个任务到达 `PENDING_QA`、`DONE`、`BLOCKED` 或 `ABANDONED` 时，负责人必须立即向项目经理回执，不能静默结束或仅变为 `idle`。
- 回执固定写明：任务名称、终态、完成内容或阻塞根因、证据（文件/runId/样本/测试报告/浏览器记录）、遗留项、下一动作。
- 项目经理收到 `DONE` 回执后，必须即时向用户报告：完成了什么、是否已通过独立浏览器验收、是否为总任务结单；没有总任务门禁证据时只能报告子项完成。

## 十二、每项任务流转强制门禁（不得跳过）

本节适用于每一项任务从登记、评审、派单、运行、测试到关闭的全部流转。项目经理必须逐项核对；任一项缺失时，任务不得进入下一状态。

### 1. 登记和派单前

- 核对目标会话的项目路径、角色和负责人，禁止跨项目错派。
- 明确用户目标、时间/数据范围、样本、不可触碰范围、最小成功证据和关闭条件。
- 对采集、回算、同步、删除等数据任务，明确精确 `runId`、source/account、触发方式、时间窗、数据上限和去重边界；“incremental”不能替代这些字段。

### 2. 运行前

- 采集/同步必须同时存在并可审计：有效时间窗口、source 范围、内容类型、分页/预算上限、checkpoint 规则、去重规则和失败状态。
- 缺少时间窗口时必须拒绝启动或由服务端注入；绝不能退化为全历史扫描。
- 必须设定首轮异常熔断阈值（例如抓取量、评论量、运行时长、重复率）；超过阈值立即停止扩张并报告，不得把持续增长解释为正常。
- 对破坏性操作，先只读解析精确目标和影响范围；停止确认终态且无 lease/写入后才能删除。

### 3. 运行中

- 项目经理按巡检节奏核对 run 状态、有效时间窗、计数、errorCode、checkpoint 和实际数据发布时间范围；不得只看 HTTP 成功或 `incremental` 标记。
- 发现时间窗缺失、越界内容、计数异常、无终态或无 progress 证据时，立刻标记异常、冻结扩大动作、定位唯一根因；未经用户明确授权不得重试/补跑。
- “等待”必须有明确前置条件，并行期必须安排无文件冲突的诊断、测试准备或下一单拆解；不得让项目组整体空转。

### 4. 测试和关闭前

- 验收同时核对：请求参数、服务端实际窗口、数据库发布时间范围、去重结果、任务终态、错误码、用户页面和通知/outbox 影响。
- 子项、候选或隔离 QA 通过，只能流转到 `PENDING_QA`；未取得真实业务运行和浏览器证据，不得写为修复完成。
- 每次状态变化、阻塞、停止、删除或完成都必须即时向用户报告，并附当前证据与下一步唯一动作。
