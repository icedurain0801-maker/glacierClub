# 概览卡片顺序、风险色阶与内容总数拆分

## 一句话需求

概览卡片调整为“今日发布内容 → 关注级内容 → 负面待处理 → 当前告警”；今日发布内容显示帖子/动态与评论的合计，并在总数下方分别显示两类数量；三张风险卡片按紧急程度逐级加深红色。

## 用户已确认口径

1. 卡片从左到右固定为：今日发布内容、关注级内容、负面待处理、当前告警。
2. “负面内容”文案统一改为“负面待处理”。该卡片数量读取最终 `severity=urgent`，不能读取所有 `sentiment=negative`。
3. “关注级内容”数量读取最终 `severity=attention`；与负面待处理互斥。
4. “当前告警”继续读取当前待处理告警集合，不把历史已解决/误报告警计入；口径与趋势和处置模块一致。
5. 今日发布内容的总数 = 同一筛选范围内的“帖子/动态数量” + “评论数量”，不得只统计 `content_type='post'`，也不得把帖子声明的评论数当作评论内容数量。
6. 总数下方分别显示两项明细：`帖子/动态 N`、`评论 N`。明细字号小于总数，作为说明信息，不替代总数。
7. 四张卡片必须使用同一个地区、社区、平台和时间范围；切换时间范围后总数、明细和三类风险数量同步刷新。

## 视觉口径

- 今日发布内容保持中性基础色，不表达风险。
- 关注级内容使用浅红/浅粉底色和较浅红色边框。
- 负面待处理使用中红底色/边框，视觉强度高于关注级。
- 当前告警使用最深红底色/边框和最高风险强调，视觉强度高于负面待处理。
- 颜色层级只用于表达紧急程度，不能改变数字、排序或筛选逻辑；低数量不应因为颜色而隐藏。
- 卡片在桌面端四列展示，在窄屏按既有响应式规则换行，文字和明细不得溢出或遮挡。

## 数据字段建议

概览接口的 `metrics` 至少返回：

| 字段 | 含义 |
|---|---|
| `total` / `newCount` | 帖子/动态 + 评论的总数 |
| `postDynamicCount` | `content_type='post'` 的内容数，BigPlayer 根据原始 JSON `type` 仅影响展示为“帖子/动态”，不重复计数 |
| `commentCount` | `content_type='comment'`（含评论内回复）的实际入库内容数 |
| `attention` | 最终 `severity='attention'` 数量 |
| `negativePending` | 最终 `severity='urgent'` 数量 |
| `activeAlertCount` | 当前 `pending/processing` 告警数量 |

若保留旧字段 `negative`，只能作为兼容字段，不得驱动新卡片文案或数量，避免将“所有负面情感”误显示为“负面待处理”。

## 产品验收样本与边界

以截图 `C:\Users\Administrator\AppData\Local\Temp\codex-clipboard-c306cc45-4b67-4148-b124-21d8872f2886.png` 的同一概览筛选范围为基准：

1. 原顺序为“今日发布内容、负面内容、关注级内容、当前告警”，验收后必须变为“今日发布内容、关注级内容、负面待处理、当前告警”。
2. 当前示例总数为 135 时，改版后应能同时看到总数 135 及帖子/动态、评论两个明细；明细相加必须等于 135。
3. 当前示例“负面内容 0、关注级内容 21、当前告警 0”仅用于验证位置和口径；实际数值必须由同一接口按当前窗口计算，不得写死截图数字。
4. “负面待处理”数量必须与内容管理 `riskMode=negative`（最终 urgent）列表总数一致；“关注级内容”必须与 `riskMode=attention` 列表一致；两者交集必须为 0。
5. 切换“今天/昨天/近7天/近30天”后，四张卡片总数、帖子/动态明细、评论明细、关注级、负面待处理和当前告警全部重新请求并与对应列表/模块一致。
6. 空数据时保留四张卡片并显示 0；不能因为当前告警为 0 隐藏卡片，除非已有产品规则明确要求隐藏告警模块本身（本需求不改变该规则）。

## 范围外

- 不改变抓取、评论入库、翻译、分析模型或风险分级算法本身；本需求只消费最终数据口径。
- 不改变卡片点击跳转、右上角地区/社区组件和时间范围记忆机制。
- 不执行发布、数据库迁移或服务重启。
