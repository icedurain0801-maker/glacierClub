# BigPlayer 9/22 当日内容未进入抓取窗口

## 用户反馈

用户反馈：9/22 执行的 BigPlayer 抓取任务，没有抓到 9/22 发布的帖子和评论。

## 已核实样本

- `runId`: `3a245915-416b-45c0-93b5-b78be30f9da4`
- 来源：境内 / 超能世界国服版 / BigPlayer
- 运行类型：`scheduled_catchup`
- 同步模式：`incremental`
- 运行状态：`completed_authorized_scope`
- 数据库只读诊断脚本：`.temp/diagnostics/inspect-run-3a245915.js`

运行记录（数据库为 UTC，页面按北京时间展示）：

- 实际开始：`2026-09-21 16:01:09Z`（北京时间 9/22 00:01:09）
- 实际结束：`2026-09-21 16:06:24Z`（北京时间 9/22 00:06:24）
- 任务调度槽：`2026-09-21 16:00:00Z`（北京时间 9/22 00:00:00）
- 实际抓取窗口：`2026-09-14 16:00:09Z` 至 `2026-09-21 16:00:09Z`（北京时间 9/15 00:00:09 至 9/22 00:00:09）

实际结果：

- 关联帖子 1236 条，最晚发布时间为 `2026-09-21 02:21:25Z`（北京时间 9/21 10:21:25）。
- 关联真实评论 4265 条，最晚发布时间为 `2026-09-21 02:12:46Z`（北京时间 9/21 10:12:46）。
- `inserted_count=0`，帖子为 `changed=1236`；评论为 `changed=96`、`unchanged=4169`。
- 运行记录中的“评论 4717”是帖子声明评论数汇总，不等于本次实际抓取的评论正文数量。

结论：不是 9/22 没有内容，也不是授权失败；9/22 00:00:09 之后发布的内容被窗口上界排除，因此当天帖子和评论均不会进入本次运行。

## 根因定位

调度链路为 `worker/src/scheduleSlots.js` → `worker/src/sourceScheduler.js` → `worker/src/schedulerRepositoryAdapter.js`：

1. `computeSchedule()` 以北京时间每天 2:00 为锚点计算槽位。
2. `collectionWindowForSlot()` 对槽位生成“前一自然日 00:00 至当前自然日 00:00”的窗口。
3. 本次是 `scheduled_catchup`，但仍沿用了调度槽对应的自然日窗口；运行在 9/22 00:01 后开始，窗口却在 9/22 00:00 截止。
4. `boundedWindowFor()` 发现已有 `schedule.window` 后直接返回，没有将窗口上界校正为本次实际执行时刻或明确的抓取截止时刻。

因此，调度槽、实际执行时间和抓取窗口上界不一致，导致“任务已完成”但当天内容天然不可见。

## 修复口径（交开发负责人）

- 定时增量抓取的窗口上界必须覆盖本次实际执行时刻；不得因为 `scheduled_catchup` 或自然日锚点把当天内容截断在 00:00。
- 窗口下界继续遵循上次成功游标/频率策略，不能重复全量扫描，也不能跳过游标之后的新内容。
- 帖子和评论必须使用同一套时间边界语义：`published_at < windowEnd`，边界时刻的内容只能按统一规则处理，不能帖子和评论各自不同。
- 运行记录的 `scheduled_at`、`started_at`、`window_start/window_end` 必须在页面可解释；若窗口被截断或回退，必须记录原因。
- 运行完成不能仅凭“请求成功”判定正常：至少展示新增、变更、未变化、跳过/越界数量，并能区分“窗口内确实无数据”和“窗口未覆盖当天”。
- 本次问题范围只涉及 BigPlayer 定时增量抓取；Discord、TapTap 及手动同步不扩大改动范围，但应补回归，确保不会受统一窗口逻辑影响。

## 页面与数据展示要求

- 抓取任务详情同时提供帖子和评论两个 scope 的真实抓取结果；“帖子声明评论数”与“真实评论正文数”分开命名和统计。
- 对于本次样本，详情应能明确显示窗口为 9/15 00:00:09 至 9/22 00:00:09，并提示 9/22 00:00:09 之后内容不在本次窗口内。
- 若任务发生 catchup，页面应显示“按实际补跑时刻截止”或等价文案，避免用户误以为任务覆盖到页面打开时刻。

## 建议验收用例

1. 前置：BigPlayer 6 小时任务在北京时间 9/22 00:01 执行，源站存在 9/22 00:00:10 发布的帖子和评论 → 操作：执行一次定时补跑 → 预期：帖子和评论都进入本次运行，且发布时间不晚于统一 `window_end`。
2. 前置：服务错过多个槽位后在 9/22 10:00 恢复 → 操作：执行 `scheduled_catchup` → 预期：只补最近一个未处理槽，但窗口上界不早于实际执行时刻，不排除 9/22 当天内容。
3. 前置：同一内容发布时间恰好等于 `window_end` → 操作：执行抓取 → 预期：按统一的开闭区间规则处理，帖子与评论结果一致，并在运行证据中可追溯。
4. 前置：窗口内没有新内容，但接口请求成功 → 操作：执行抓取 → 预期：显示“窗口内无新增”，不得伪装成“抓取到 0 条当天内容”或直接归因授权失败。
5. 前置：运行同时包含帖子声明评论数和真实评论正文 → 操作：查看任务详情 → 预期：两类数量分开显示，不能把声明评论数当作真实抓取评论数。
6. 前置：Discord、TapTap 定时任务各有一条当天内容 → 操作：执行回归 → 预期：既有窗口和抓取结果不发生回退。
